# Microcontroller Startup Code Explained: Reset Handler, Vector Table, and Runtime Init

When a microcontroller powers on or resets, it does not begin by calling the application's main() function directly. The processor follows an architecture-defined reset sequence and executes startup code that prepares memory and runtime state.

Understanding this sequence is useful when debugging early boot failures, linker configuration issues, vector tables, and application handover from a bootloader.

## What happens after reset?

A simplified startup flow is:

1. Processor reset is released.
2. CPU loads the initial stack pointer and reset handler according to its architecture.
3. Reset handler performs low-level initialization.
4. Initialized data is copied to RAM.
5. BSS memory is cleared.
6. Clocks and essential hardware are configured as required.
7. C runtime initialization executes.
8. The application enters main() or the configured RTOS startup path.

The exact reset behavior differs between architectures. For example, many Cortex-M microcontrollers load the initial stack pointer and reset vector from the vector table.

## What is a vector table?

The vector table contains addresses or entries used to dispatch reset and exception/interrupt handlers.

On Cortex-M systems, the first vector entries commonly include the initial stack pointer and reset handler address, followed by exception handlers and external interrupt handlers.

Other processor architectures use different vector and exception mechanisms.

The vector table must be located and aligned according to the processor's requirements.

## Reset handler

The reset handler is the first software entry point after the processor's reset sequence.

A simplified C-like outline:

~~~c
void Reset_Handler(void)
{
    initialize_data();
    clear_bss();
    initialize_hardware();
    runtime_init();
    main();

    for (;;) {
        /* main should not normally return */
    }
}
~~~

This is illustrative only. Real startup code is often written in assembly or generated by the vendor toolchain and uses linker-defined symbols.

## Copy the .data section

Global and static variables with initial values are commonly placed in the .data section at runtime.

The initial values are stored in a load image, often in flash. Startup code copies them to the runtime RAM address before the application uses them.

If the copy is incorrect, initialized variables may contain unexpected values.

## Clear the .bss section

Global and static variables that are not explicitly initialized are commonly placed in .bss.

Startup code clears this region so those objects begin with zero values as required by the C runtime environment.

A missing or incorrect BSS initialization can cause failures that appear unrelated to the code using the variable.

## Clock and low-level hardware initialization

The reset clock may be a default internal source. Startup or early system code may configure:

- Oscillator and PLL.
- Clock dividers.
- Flash wait states.
- Memory protection.
- Cache and TCM.
- FPU access.
- External memory controllers.
- Pin and power configuration.

The safe order is device-specific. For example, a clock increase may require flash wait-state configuration before switching to the higher frequency.

Use vendor startup code and reference manuals as the baseline.

## C runtime initialization

The C runtime may initialize constructors, library state, and other execution environment details before main() is called.

C++ systems additionally require static object constructors to run according to the toolchain's startup mechanism.

Do not bypass runtime initialization unless the system intentionally uses a different execution model and all required initialization is provided.

## Startup code and the linker script

Startup code often references linker symbols that identify:

- .data load and run addresses.
- .data start and end.
- .bss start and end.
- Stack region.
- Heap region.
- Vector table location.
- Application image boundaries.

The linker script and startup implementation must agree. If a section name or memory region changes, the startup copy and zeroing operations may need to change as well.

## Bootloader handover

A bootloader may jump to an application reset handler after validating an image.

It must prepare the CPU state and vector-table location according to the target architecture and application assumptions.

Potential concerns include stack pointer, interrupt state, pending exceptions, cache, MPU configuration, clock settings, and peripheral ownership.

A direct function call to an application reset handler is not necessarily a safe handover.

## Debugging early startup failures

If the application fails before main(), inspect:

1. Reset cause and boot mode.
2. Vector table address and contents.
3. Reset handler symbol and address.
4. Stack pointer and memory mapping.
5. .data load and run addresses.
6. BSS clearing range.
7. Clock and flash wait-state setup.
8. Fault status registers.
9. Linker map and startup disassembly.

Use a debugger capable of connecting at reset or under a controlled halt sequence. Early boot faults may occur before normal logging is available.

## Common mistakes

### Wrong vector table address

The processor or interrupt controller may read vectors from a different address than the application expects.

### Incorrect stack pointer

A stack outside valid RAM or with insufficient size can cause immediate faults.

### Incorrect BSS or data range

A wrong linker symbol can cause memory corruption or missing initialization.

### Changing memory layout without updating startup code

Linker and startup assumptions must be kept consistent.

### Skipping required runtime initialization

C and C++ programs may depend on initialization that occurs before main().

## Frequently asked questions

### Does main() run immediately after reset?

Usually not. A reset handler and runtime initialization sequence execute first.

### Why are global variables zero after reset?

The C runtime startup code commonly clears the .bss section before main() is called.

### Is startup code the same across every MCU?

No. It depends on processor architecture, vendor, toolchain, memory layout, and product boot architecture.
